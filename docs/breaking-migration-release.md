# 後方互換でないデータ移行のリリース手順

本書は、**旧コード × 新DB でも 新コード × 旧DB でも壊れる**変更を本番へ出すときの手順を定める。通常の本番反映の操作手順（バックアップ、`migration list` / `db push`、`release` へのマージ、ロールバックの操作面）は Wiki の [本番環境リリース手順](https://github.com/Singuralitylabs/sinlab-study/wiki/本番環境リリース手順) を正とする。本書はその上に載せる「両立窓をどう設計するか」の方針である。

マイグレーションファイルの置き方・開発用プロジェクトへの適用・型再生成は [`docs/database.md`](./database.md) 7 章を参照する。

---

## 1. 対象になる変更

次のいずれか（または両方）に当てはまる変更は、SQL 適用とアプリデプロイのどちらを先にしても壊れる窓が開く。

| 種類 | 例（#214 / v2.2.0） | 窓の症状 |
|:--|:--|:--|
| 既存データの値・形式の書き換え | `users.status` の `pending` → `trial`、`learning_contents.pdf_url` の公開 URL → オブジェクトキー正規化 | 旧コードが旧形式を前提に組み立て・INSERT するため、新DBでは登録失敗やスライド全滅 |
| 新コードが前提とする DB オブジェクトが旧DBに無い | `slides` バケットの SELECT ポリシー新設、バケットの非公開化 | 新コードの `createSignedUrl()` が RLS で拒否され、全ユーザーでスライド全滅 |

「カラム追加のみ」「NULL 許容のまま読むだけ」など、**新旧どちらでも動く変更は本書の対象外**である。Wiki の通常手順（必要なら SQL 先行）でよい。

---

## 2. 原則: 3 段リリース（expand / migrate / contract）

可能な限り次の 3 段に分ける。各段は別 PR（または少なくとも別デプロイ）とし、前段が本番で安定してから次へ進む。

### 段 1 — Expand（新旧どちらでも動くコードを先に出す）

アプリが **旧値と新値の両方**を受け入れる状態にする。データはまだ書き換えない。DB 側も、この段では「新オブジェクトの追加」や「制約の緩和」までに留める。

例:

- **ステータス値のリネーム**: `ALLOWED_USER_STATUSES`（および proxy の許可リスト）に一時的に `pending` と `trial` の両方を入れる。新規 INSERT はまだ旧値のまま、または新旧どちらでも CHECK が通る状態にする
- **`pdf_url` の形式変更**: 読み取り側で旧形式の公開 URL もオブジェクトキーへ正規化する（`toSlideObjectKey()` が既にこの形）。書き込み側もキーへ正規化して保存する

この段が本番に乗った時点で、次の SQL を流しても旧コードが残っていても致命傷にならない。

### 段 2 — Migrate（データ移行 SQL を適用する）

既存行の UPDATE、CHECK 制約の差し替え、バケット公開設定の変更など、**データを新形式へ寄せる SQL** を適用する。段 1 のコードが両方を読める前提なので、適用直後もサービスは動き続ける。

破壊的な UPDATE の前に対象件数を確認し、逆 SQL（後述）を手元に置く。

### 段 3 — Contract（旧値の受け入れを削除する）

旧値・旧形式の分岐をコードから削除する。CHECK 制約やポリシーも新値のみに絞る。ここまで終わって初めて移行完了とする。

---

## 3. 分割できる変更は分割する

1 つの機能 PR に「アプリ変更」と「DB 変更」が同居していても、**旧コードに影響しない DB 変更は先行リリースできる**。

典型例:

- **Storage の SELECT ポリシー追加**: 旧コードが公開 URL 経由で PDF を読んでいれば、SELECT ポリシーの追加だけでは旧コードは壊れない。新コードが `createSignedUrl()`（RLS 適用の通常クライアント）を使うなら、ポリシーが無い旧 DB では全滅する。よって **ポリシー追加だけを段 1 相当として先に適用**し、その後にアプリの署名付き URL 化とバケット非公開化・`pdf_url` 正規化を出す
- **新しい RPC / カラムの追加（旧コードが未参照）**: 追加だけ先に流し、参照するコードを後からデプロイする

逆に、**値のリネームと、その値を参照する RLS ポリシーの書き換え**のように、片方だけ適用すると即破綻するものは同一トランザクション（同一マイグレーションファイル）にまとめ、3 段の「段 2」として扱う（`docs/database.md` マイグレーション一覧の `rename_pending_status_to_trial` の注記と同じ判断）。

---

## 4. 3 段に分けられない場合の運用

設計上どうしても expand を挟めない、またはリリース日までに 3 段を回せないときは、**窓を短くする運用**に落とす。窓を無くす代替ではない。

1. **適用する SQL を事前に用意する** — Supabase SQL Editor のタブ、または手元のスクリプトに、実行順どおり並べておく。`db push` でまとめて流せるならその手順を Wiki Step 3 に従って準備する
2. **デプロイ完了を待って即実行する** — Vercel の Production デプロイが Ready になった直後に SQL を流す（または、バッチ分割で「旧コードに影響しない SQL」を先に流し、「両立しない SQL」だけをデプロイ直後に流す）
3. **途中で失敗しても最後まで流し切る** — 中断したまま放置すると、締め出しやスライド全滅が続く。失敗した文の原因を直して続きを適用するか、事前に用意したロールバックで一旦戻すかをその場で決める（「様子見」で止めない）
4. **窓の間に何が壊れるかを PR 本文に列挙する** — 例: お試しユーザーのログイン不可、新規 Google 登録の `registration_failed`、全ユーザーのスライド閲覧不可。レビュアーと作業者が同じ前提を共有するため必須

v2.2.0（#214）はこの運用で窓を数十秒に抑えた。バッチ分割は正しい判断だったが、手順として残していなかったため本書で明文化する。

---

## 5. ロールバック

既存データを書き換える変更では、**逆 SQL を作業前に用意することを必須**とする。

- Vercel の **Instant Rollback はコードだけ**を戻す。DB が既に新形式（値リネーム、URL 正規化、バケット非公開化など）へ進んでいると、ロールバック後の旧コード × 新 DB で再び壊れる
- 逆 SQL は「段 2 で何をしたか」の対になること（UPDATE の戻し、制約の戻し、ポリシー削除、バケットの公開設定戻し）。件数確認用の SELECT もセットで置く
- ロールバック可否の最終判断と操作手順は Wiki のロールバック節に従う。本書は「コードだけ戻せばよいと思わない」ことを要求する

---

## 6. リリース PR 本文に書くチェック項目

後方互換でないデータ移行を含むリリース PR（base: `release`）では、テンプレートの「その他」「レビュー特記事項」「動作確認内容」に、少なくとも次を書く。

- [ ] **適用順序の制約** — 3 段のどの段か / SQL 先行かデプロイ直後か / 分割したバッチの依存関係
- [ ] **窓の間に壊れるもの** — ユーザー種別・機能単位で列挙（「壊れるものなし（expand 済み）」でも明記）
- [ ] **逆 SQL の用意** — 置き場所、または PR / 作業メモへの貼付。Instant Rollback だけでは足りない旨
- [ ] **破壊的変更の対象件数** — 本番（または本番相当）で確認した UPDATE 対象行数・影響バケット

機能 PR（base: `main`）の段階でも、後で 3 段に分ける予定なら「TODO 事項」に残すか、最初から PR を seg 分割する。

---

## 7. 判断フロー（要約）

```text
旧コード×新DB または 新コード×旧DB で壊れるか？
  ├─ No → Wiki の通常リリース手順
  └─ Yes
       ├─ expand（両対応コード / 無害な DB 追加）を先に出せるか？
       │    ├─ Yes → 3 段リリース（§2）。分割できる DB 変更は §3 で先行
       │    └─ No  → 短窓運用（§4）。逆 SQL 必須（§5）。PR に §6 を記載
       └─ いずれの場合も本番操作は Wiki に従う
```
